# Terraform AWS Infrastructure with Remote State Management

## Architecture Overview

This project provisions AWS infrastructure using Terraform with modular design and automated remote state management:

**Backend Layer:**
- S3 bucket for state storage (versioning + encryption enabled)
- DynamoDB table for state locking (prevents concurrent modifications)

**Networking Layer:**
- VPC with custom CIDR block
- Public subnet with auto-assign public IP
- Internet Gateway for internet connectivity
- Route table with public internet route
- Security group (SSH port 22, HTTP port 80)

**Compute Layer:**
- EC2 instance (t2.micro, Amazon Linux 2)
- Apache web server with sample page
- Optional SSH key pair support

All resources are parameterized, tagged, and deployed with automated scripts.

## How It Works - Deployment Flow

**Step-by-Step Deployment Process**

```
deploy.sh → Backend Module → backend.tf Generation → Main Infrastructure → Outputs
```

### 1. Backend Deployment
- Script runs `modules/backend` to create S3 bucket and DynamoDB table
- S3 bucket configured with versioning, encryption, and public access blocking
- DynamoDB table created for state locking

### 2. Backend Configuration Auto-Generation
- Script captures outputs: `s3_bucket_name`, `dynamodb_table_name`, `region`
- **Automatically generates** `backend.tf` with real values:
  ```hcl
  terraform {
    backend "s3" {
      bucket         = "terraform-state-abraham-gyamfi-2026"
      key            = "terraform.tfstate"
      region         = "eu-west-1"
      dynamodb_table = "terraform-state-lock"
      encrypt        = true
    }
  }
  ```

### 3. State Migration
- Main Terraform initializes with `terraform init -migrate-state`
- Local state automatically migrated to remote S3 backend
- DynamoDB locking enabled to prevent concurrent modifications

### 4. Infrastructure Deployment
- Networking module creates VPC, subnet, IGW, route table, security group
- Compute module launches EC2 instance with Apache web server
- User data script installs and starts httpd service

### 5. Access & Testing
- EC2 instance accessible via public IP
- Apache serves sample page: "Hello from Terraform! Instance: ..."
- SSH access available (if key pair configured)

## Security Design

- **Encrypted State**: S3 bucket uses AES256 encryption
- **Versioned State**: S3 versioning enabled for rollback capability
- **State Locking**: DynamoDB prevents simultaneous modifications
- **Private Bucket**: Public access completely blocked on S3
- **Restricted Access**: Security group limits SSH to specific IPs
- **Tagged Resources**: All resources tagged for tracking

## Deployment Instructions

1. **Clone the repository**
   ```bash
   git clone git@github.com:AbrahamGyamfi/Terraform_state_file.git
   cd Terraform_state_file
   ```

2. **Configure AWS credentials**
   ```bash
   aws configure
   # Or export AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY
   ```

3. **Edit configuration**
   ```bash
   cp terraform.tfvars.example terraform.tfvars
   # Edit terraform.tfvars with your values
   ```

4. **Run automated deployment**
   ```bash
   chmod +x deploy.sh
   ./deploy.sh
   ```

The script automatically:
- Deploys backend infrastructure
- Generates backend.tf configuration
- Migrates state to S3
- Deploys main infrastructure
- Displays all outputs

## Module Descriptions

**backend**: S3 bucket (versioned, encrypted) + DynamoDB table for state management  
**networking**: VPC, public subnet, IGW, route table, security group (ports 22, 80)  
**compute**: EC2 instance (t2.micro, Amazon Linux 2) with Apache web server

## Variables

See each module's `variables.tf` for all options. Key root variables:

**Required/Recommended:**
- `aws_region` (default: `us-east-1`)
- `project_name` (default: `terraform-lab`)
- `allowed_ssh_cidr` (**Important**: Set to `YOUR_IP/32` for security)
- `key_name` (optional: SSH key pair name)

**Networking:**
- `vpc_cidr` (default: `10.0.0.0/16`)
- `subnet_cidr` (default: `10.0.1.0/24`)
- `availability_zone` (default: `us-east-1a`)

**Compute:**
- `instance_type` (default: `t2.micro`)
- `ami_id` (default: Amazon Linux 2 in us-east-1)

## Outputs

**VPC Resources:**
- `vpc_id`: VPC identifier
- `subnet_id`: Public subnet identifier
- `internet_gateway_id`: Internet Gateway identifier
- `security_group_id`: Security group identifier

**Compute Resources:**
- `ec2_instance_id`: EC2 instance identifier
- `ec2_public_ip`: Public IP address of EC2 instance
- `ec2_public_dns`: Public DNS name of EC2 instance
- `ssh_connection_command`: Ready-to-use SSH command

**View outputs:**
```bash
terraform output
```

**Test web server:**
```bash
curl http://$(terraform output -raw ec2_public_ip)
```

## Cleanup

**Automated cleanup:**
```bash
./destroy.sh
```

The script will:
1. Destroy main infrastructure (EC2, VPC, etc.)
2. Ask if you want to destroy backend (S3 + DynamoDB)

**Manual cleanup:**
```bash
terraform destroy
# Optionally destroy backend
cd modules/backend && terraform destroy
```

## Troubleshooting

**S3 bucket already exists**: Change `bucket_name` in `modules/backend/terraform.tfvars` (must be globally unique)

**Backend configuration changed**: Run `terraform init -reconfigure`

**State locked**: Wait for operation to complete or check DynamoDB console

**AMI not found**: Update `ami_id` for your region:
```bash
aws ec2 describe-images --owners amazon \
  --filters "Name=name,Values=amzn2-ami-hvm-*-x86_64-gp2" \
